# OrbitParts audit (2026-11-25)

A read-only deep dive into the whole app at commit `2c605d1`: nine parallel code reviews (BOM and
dashboard; To Fab and drawings; Orders; Inventory; shop map and Settings; CAD page and 3D viewer;
Design check and Assembly; Onshape, MCP and security; shell, performance, egress, ops and code
health), a walk through the local site at phone (375 px) and laptop (1366 px) width, the `/dev/*`
sandboxes, and one request to the live site's public health check. No code was changed, no SQL ran
on production, nothing was deployed.

Every finding has a place (`file:line` at `2c605d1`), why it matters, a fix, a severity (**bug** /
**important** / **nice-to-have**) and an effort (**S** hours, **M** a day or two, **L** more). The
reviewers traced each one in the code, and I re-read the key ones myself ("✔ re-read").
"(?)" marks a number or an effect that wasn't measured (usually a byte size on production).

## Summary

About 370 findings from the nine reviews and the UI walk (roughly 60 bugs, 95 important, 215
nice-to-have), merged here into 219 entries. The app is in much better
shape than on 14 Nov: every server action and route checks its capability, MCP follows the role and
status rules, search and arrivals are cached, deploys wait for the tests. What's left clusters into
a few themes:

1. **The nightly SQL backup isn't running.** The live `/api/cron/health` answers
   `503 {"failing":["sqlBackup"]}` today. The JSON backup works but has no members, part history,
   versions, CAD comments, assembly steps, design checks, order history or carts. Check the timer on
   the VM first (§0, OPS-1).
2. **The new multi-process model (2026-11-20) loses work through normal shop taps.** "+" on the next
   process skips a pending QA; batching a QA-approved part, the batch status menu, section drops and
   several status picks send Process-2 parts back to Process 1 with their counts and QA tick wiped;
   "Select all → Release" re-releases parts already in process (BOM-1, BOM-2, BOM-4, BOM-7, FAB-1…3).
3. **Receiving and ordering maths drift.** A restock card and a BOM part order the same units twice;
   arrivals are recomputed at arrival instead of frozen; a typed amount can be received twice;
   arrivals land on the first variant instead of New, so the new New-need re-orders forever
   (ORD-2…5).
4. **Supabase egress is still spent per tap.** Each save re-renders the page through
   `revalidatePath`, and table-wide cache counters make that re-read every part of the robot (or
   the whole shelf, every place, the materials list) per "+" tap; the BOM 3D model reads the Final
   model too and throws it away; CAD comment actions render the page twice. A day or two of small
   fixes (PERF-1…7) cuts much of it; trimming the system page's reads (PERF-8) and per-robot or
   delta reloads (PERF-9) cut the rest. Measure first (PERF-10): nothing here was sized on
   production.
5. **A dropped connection still crashes whole pages** on Orders, Settings, the CAD page, Update
   System, most inventory windows, Assembly ticks, the drawing editor and Design check. One
   `safeAction` sweep fixes it (X-1).
6. **Permission mismatches show buttons that always fail:** Build Team's QA check, Build/CAD's
   "In Stock?" on order cards, Done boxes for teamless members (X-2).
7. **Security:** the Onshape-panel sign-in can still hand a member's whole account to an outsider for
   60 days with one approved click; MCP confirm tokens can be replayed (a retry moves stock twice);
   inventory photo and zone picture uploads have no size check (R2's free 10 GB); a plain GET of the
   Factory pack can spend ~200 Onshape calls (SEC-1…5).
8. **Phones:** three.js, the drawing editor, the shop map and the fab nester ship with every page
   (~30k lines); the Home pictures are 4 MB; BOM card pills are ~20 px; the system page's tools sit
   off-screen; WebGL contexts are never released, so long CAD or Assembly sessions blank the main view
   (X-5, SHL-1, X-9, BOM-16, X-4).

The highest-value work, in order, is the ranked list at the end (§13). The first six items are S–M
and fix the data loss, the crashes and most of the egress.

**BOM-1 · bug · S — One "+" on the next process skips the QA gate.** `src/lib/fab.ts:96-99`

**BOM-2 · important · S–M — Some statuses picked at a later process send a shop part back to

## 9. Onshape panel and Insert, the MCP server, security and sign-in

Coverage: a scan of every `"use server"` file found 192 exported actions, all calling a guard
(`requireMember` / `requireCapability` / `requireAdmin` / `getMember`) before their first database,
R2 or Onshape call; every one of the 50 route handlers checks the member, a capability, the MCP token
or the cron secret, except the deliberately public `/api/ready`, `/api/panel/login` and
`/api/cron/health`. MCP tools follow the role and status rules now, with batch and search limits and
per-tool destructive hints. Onshape calls time out, refreshes no longer hold a row lock, and only
`invalid_grant` disconnects.

### Security and sign-in

**SEC-1 · important · M — One approved click on a link gives an outsider a member's account for 60
days, irrevocably.** `api/panel/login/route.ts:27-54`, `onshape/connect/page.tsx:17-33,45`,
`lib/panelSession.ts:6-44`, `lib/auth.ts:33`, `supabase/proxy.ts:42`. A non-member POSTs
`/api/panel/login`, gets a code, sends a member `…/onshape/connect?code=<theirs>`; the member, signed
in, sees "Sign in to the OrbitParts panel… as <name>?" and taps it; the attacker's poll then returns
the `orbit_panel` cookie, which `getMember()` accepts on every page, action and route for 60 days.
Only deleting the member or rotating `ONSHAPE_TOKEN_KEY` (which disconnects every Onshape account)
ends it. An admin's cookie is full Edit. *Fix, in order:* (1) a device-code flow: the panel shows a
short code (`K7P-4QX`) the member types on the connect page; (2) `members.panel_epoch` in the MAC and
"Sign out of Onshape panels everywhere" on Profile; (3) accept the panel cookie only for panel traffic
(`/onshape/*`, `/api/panel/*` and the API routes the panel calls); (4) 14 days with sliding renewal.
(Old item; only a warning sentence was added.)

**SEC-2 · important · S — The panel never says who's signed in and has no sign-out.**
`onshape/panel/PanelHome.tsx:33-52`; `auth/signout/route.ts:6-12` clears the cookie only in the
partition of the page that posts it. On a shared CAD-room PC every Update BOM commit, comment and
insert from that browser is credited to whoever signed in first, for 60 days; a removed admin's
panel session keeps working there. *Fix:* "Signed in as <name> · Sign out" on every panel page, backed
by `POST /api/panel/logout` from inside the iframe (clears the right partition).

**SEC-3 · bug / important · S–M — MCP confirm tokens can be replayed, and they bind the arguments,
not the preview.** See MCP-1 and MCP-2: a client retry moves stock twice; `update_bom_from_onshape`
commits changes nobody saw.

**SEC-4 · important · S — Inventory photo and zone picture uploads have no size check.**
`inventory/actions.ts:156-183` (`startPhotoUpload` → `applyPhoto` checks only `objectExists`),
`settings/mapActions.ts:87-110`, `storage/r2.ts:60`. A presigned PUT accepts up to 5 GB and each
call hands out a fresh 10-minute URL; part and group files are checked after upload
(`files-actions.ts:64-69`), these aren't. One buggy or malicious phone could push R2 past its free
10 GB, and R2 bills overage to the card on file. *Fix:* `objectSize(key)` in `applyPhoto` /
`setZoneImage`, delete objects over ~3 MB; sign `content-length` / `content-type` into the presigned
PUT (test once that R2 enforces signed headers).

**SEC-5 · important · S–M — A plain GET of the Factory pack can spend ~150–200 Onshape calls, then
zips in memory on the one CPU.** `api/groups/[groupId]/zip/route.ts:21-89`. Any member (even with no
team) can open the link; each part not yet exported costs a translation (3–4 calls,
`onshape/export.ts:84-102`), up to 40 % of the team's day for a 50-part pack; then every file is
pulled from R2 into memory and compressed with `deflateRawSync`, blocking every request meanwhile.
The same `getMember()`-only check guards the DXF zip, the layout route's first sheet-metal flat
pattern and part exports (`dxf/route.ts:20`, `layout/route.ts:12`, `api/parts/[partId]/export/route.ts:20`).
*Fix:* export as a POST needing `work` (like Batch STEP, `onshape-layout/step/route.ts:18-42`), GET
only when every file is already exported; cache the built zip in R2 per pack and revision set; async
`deflateRaw` or store STEP / x_t uncompressed. Whether teamless members keep export rights at all is
in §12.

**SEC-6 · important · S — Database TLS doesn't verify the server, and is off when the URL lacks
`sslmode`.** `db/index.ts:10-16`: `rejectUnauthorized: false`, and without `sslmode` in the URL `ssl`
is never set (node-postgres then connects in plain text across the internet); `deploy/backup.sh`
uses libpq's `prefer`. *Fix:* in production always `ssl: { ca: DATABASE_CA, rejectUnauthorized: true }`
with Supabase's CA (Dashboard → Database → SSL), `sslmode=verify-full&sslrootcert=` for `pg_dump`,
"Enforce SSL" on in Supabase (free). Try it from the VM once before deploying. (Old item.)

**SEC-7 · nice-to-have · S — Cross-site POSTs to route handlers carry the panel cookie (no Origin
check).** `supabase/proxy.ts:12-51`; POST / PUT routes such as `api/parts/[partId]/drawing/route.ts:87`,
`api/groups/[groupId]/onshape-layout/route.ts:32,38`, `api/robots/[robotId]/model/route.ts:41`. Server
actions get Next's Origin check; route handlers don't, `request.json()` parses `text/plain`, and the

them as the member. *Fix:* in `updateSession`, 403 non-GET `/api/*` requests (except MCP, cron, panel
login) whose `Origin` isn't `publicOrigin(request)`. (Old item.)

**SEC-8 · nice-to-have · S — Secrets shared across purposes, and a hard-coded health key.**
`panelSession.ts:17-22` (panel HMAC from `ONSHAPE_TOKEN_KEY`), `mcp/confirm.ts:11` (falls back to

## 10. Performance and Supabase egress

The 14 Nov egress fixes held (search, arrivals, the model payload, indexes, the cache size cap), and
steady background traffic is small (`egress-steady.md`: ~120–145 MB a day measured on 21 Nov). What's
left grows with use: each save re-renders the page through `revalidatePath`, and the cache counters
are per table, so a write anywhere in `parts` (or `inventory_items`) makes every cached read of that
table miss. One correction to `CLAUDE.md`: with Next's partial rendering the `(app)` layout does not
re-run on a soft navigation (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/staleTimes.md:35`);
it runs on a full load, a `router.refresh()` and every action that revalidates. "Every save" is the
case that costs.

None of the byte sizes below were measured on production (no production reads, by design). PERF-10
gives real numbers for free; doing it first tells you which of the rest matter most.

### Quick wins (S each, about a day together)

**PERF-1 · important · S — The BOM 3D model reads the Final's whole model just for the Basepart's
sketches.** `model/build.ts:146-148` (`kind === "bom"` calls `loadFinalWithSketches`, which selects
